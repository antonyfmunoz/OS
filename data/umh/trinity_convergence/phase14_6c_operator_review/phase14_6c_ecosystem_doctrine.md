## 1. The UMH Reality Model (OPERATOR CLARIFICATION — P0)

**Provenance: OPERATOR_CORRECTION (verbatim, 2026-06-04)**

The 14.6B UMH canon describes UMH as a "private universal intelligence
substrate, orchestration kernel, governed execution control plane." This
framing is incomplete. The operator has issued the following correction
with P0 authority:

### 1.1 Core Correction

UMH is a reality-approximation engine. Its reality model is intended to
approximate reality as closely and isomorphically as possible. It is not
merely an operational tooling model or business/software model. It must
ultimately model the following layers as corresponding layers of one
unified reality model:

| # | Reality Layer | Description |
|---|--------------|-------------|
| 1 | Physical | Material world — objects, locations, infrastructure, devices |
| 2 | Digital | Software systems, networks, APIs, data stores, code |
| 3 | Cognitive | Mental models, reasoning, attention, decision-making |
| 4 | Biological | Health, circadian rhythms, energy, body systems |
| 5 | Social | Relationships, trust networks, communication, reputation |
| 6 | Economic | Markets, capital, transactions, value flows, revenue |
| 7 | Symbolic | Language, meaning, identity, brand, narrative, belief |
| 8 | Operational | Processes, workflows, SOPs, execution, coordination |
| 9 | Software | Architecture, code, dependencies, deployment state |
| 10 | Memory | Knowledge, experience, history, learning, context |
| 11 | Source-Truth | Canonical facts, verified claims, provenance chains |
| 12 | OS-Level | System state, permissions, scheduling, resource allocation |

### 1.2 Instance Reality Model

The instance reality model carries the same isomorphic ambition as the
universal model, but from the perspective and context of a specific
instantiated user, company, product, environment, or incarnation.

Where the universal model defines what reality layers exist and how they
relate, the instance model populates those layers with concrete state:
this user's health data, this company's revenue, this product's
deployment topology, this environment's resource constraints.

### 1.3 Materialization Principle

If a human can imagine an outcome, UMH should attempt to simulate the
path from imagination to materialization. Lack of current knowledge,
resources, tools, capital, or information does not invalidate the intent.
Instead, it creates:

- **Acquisition loops** — identify and obtain missing resources
- **Research loops** — investigate unknowns and build knowledge
- **Experiment loops** — test hypotheses and validate approaches
- **Work packets** — concrete executable units of progress
- **Time-bound execution paths** — scheduled steps toward the outcome

The principle means UMH is not a passive observer of reality. It is an
active engine that maps the gap between current state and desired state,
then generates governed execution paths to close that gap. The gap may
span any combination of reality layers.

## 2. The Indivisible Stage 1 Organism

**Provenance: OPERATOR_CORRECTION (2026-06-04)**

### 2.1 Core Correction

The 14.6B artifacts describe a sequential Stage 1 build:

1. First: build the execution harness (substrate, model routing, governance)
2. Then: build the Cockpit (panels, API, frontend)
3. Then: build the reality model (world model, memory, simulation)

This sequencing is incorrect. The operator has corrected:

**Stage 1 is ONE minimum viable organism:**

```
Reality Model + Cockpit + Memory + Governed Execution Loop = ONE THING
```

These four components are indivisible. They must be built and validated
together because:

- **Cockpit without a reality model = only a dashboard.** It can display
  operational state but cannot show the operator what reality looks like.
  The operator cannot reason about gaps between current reality and
  desired reality. Cockpit becomes a monitoring tool, not a command surface.

- **Reality model without Cockpit = inaccessible to the operator.** The
  model may be internally consistent but the operator cannot observe it,
  query it, correct it, or use it to make decisions. An invisible model
  is an inert model.

- **Harness without reality model = cannot function as intended.** The
  execution harness routes signals, classifies risk, and coordinates
  agents — but without a reality model, it has no grounding for what
  "risk" means in context, what "state" looks like across layers, or
  what "progress" means toward a desired outcome.

- **Memory without reality model = accumulation without structure.** Memory
  stores facts, observations, and decisions, but without reality layers
  to organize them, memory is a flat knowledge base rather than a
  structured understanding of reality.

| Reality model timeline | "Future phase" per several artifacts | Stage 1 — same timeline as harness and Cockpit |
| Memory architecture | Operational memory store | Structured reality-model memory organized by reality layers |
| World model role | "Understanding subsystem" | Core reality engine — the purpose of UMH, not a feature of it |

## 8. Cross-Product Integration Model

**Provenance: umh_cross_product_integration_architecture.md +
umh_eos_creatoros_lyfeos_integration_map.md + projection integration code**

### 8.1 How Projections Register with UMH

Each projection registers via an integration manifest that declares:

1. **Signals emitted** — what event types the projection produces
2. **Capabilities exposed** — what actions UMH can take on the projection
3. **Polled tables** — which database tables UMH monitors for new data
4. **Configuration** — database URL, poll interval, user ID whitelist

| Projection | Signals | Capabilities | Polled Tables | Integration Lines |
|-----------|---------|-------------|--------------|-------------------|
| EOS | CRM events, workflow events, entity events | Full department agent actions | CRM tables | 5,699 (full projection) |
| CreatorOS | post_created, product_listed, revenue_recorded | create_post, create_product, record_revenue, noop | posts, products, revenue | 1,099 (integration layer) |
| LyfeOS | quest_completed, stats_updated, daily_log_created | create_quest, complete_quest, log_daily_reflection, noop | quests, user_stats, user_daily_logs | 1,184 (integration layer) |

### 8.2 Signal Flow

```
Projection Database
    |
    | (UMH polls new rows on configurable interval)
    v
SignalEmitter (projection-specific)
    |
    | (builds SignalEnvelope with source, urgency, content)
    v
UMH Execution Pipeline
    |
    | (interpret -> recall -> route -> execute -> trace -> feedback)
    v
CapabilityHandler (projection-specific)
    |
    | (writes result back to projection database)
    v
OutcomeReceiver (projection-specific)
    |
    | (dual writeback: source row umh_status + umh_outcomes audit table)
    v
Projection Database (updated)
```

### 8.3 Cross-Projection Workflow (Future)

Cross-projection workflows route through UMH, never peer-to-peer.
Example: a business win in EOS triggers content creation in CreatorOS
and a wealth stat update in LyfeOS.

```
EOS: Client signs contract
    |
    | (EOS signal: client_contract_signed)
    v
UMH: Interpret -> Decompose -> Route
    |
    +---> CreatorOS capability: create_post
    |     (case study content from contract details)
    |
    +---> LyfeOS capability: update_stat
    |     (wealth token increment from revenue)
    |
    +---> Cockpit: notify operator
          (cross-projection workflow completed)
```

This is NOT implemented. Current state: each projection operates
independently. Cross-projection signal routing requires governance
policy, data boundary rules, and operator approval.

## 9. What UMH Must NOT Become

**Provenance: umh_projection_ecosystem_doctrine.md + all four product canons + operator corrections**

### 9.1 Anti-Patterns

| Anti-Pattern | Why It Is Wrong | What To Do Instead |
|-------------|----------------|-------------------|
| **Mega-app** | UMH is a substrate, not a user-facing application. Combining all projection features into one app destroys domain-specific UX. | Keep projections separate with distinct UX, data models, and user bases. |
| **Chatbot** | UMH's intelligence is governed and structured. A chatbot is an unstructured conversational interface. UMH classifies, decomposes, governs, and executes — it does not "chat." | Use agents with defined roles, authority tiers, and governance. Chat is one input channel, not the system identity. |
| **SaaS wrapper** | UMH is private infrastructure. Wrapping it in SaaS UX confuses platform with product. | Projections are the SaaS products. UMH stays private. |
| **Tool collection** | UMH is not a bag of unrelated tools. Every capability serves the reality model and execution pipeline. | Capabilities compose into a coherent pipeline. No orphan tools. |
| **Dashboard** | Dashboards display. UMH acts. Cockpit is not a dashboard — it is a command surface. | Cockpit must be commandable, not just observable. Every display must be actionable. |
| **Single-domain product** | UMH is universal. Collapsing it to serve only EOS or only one business domain destroys the multi-projection architecture. | Keep substrate projection-agnostic. Domain logic lives in projections/. |
| **Passive observer** | Per the materialization principle, UMH does not just model reality — it actively generates paths from current state to desired state. | Always generate acquisition loops, research loops, work packets when gaps are detected. |
