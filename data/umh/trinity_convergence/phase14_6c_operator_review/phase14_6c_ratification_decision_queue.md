The following operator correction was received during Phase 14.6C review and must be treated as a P0 input that potentially affects 17 UMH artifacts and all downstream Cockpit/reality-model/governance specifications.

> The UMH reality model is intended to approximate reality as closely and isomorphically as possible. It is not merely an operational tooling model or business/software model. It must ultimately model physical, digital, cognitive, biological, social, economic, symbolic, operational, software, memory, source-truth, and OS-level reality as corresponding layers of one reality model.
>
> The instance reality model carries the same isomorphic ambition, but from the perspective/context of a specific instantiated user, company, product, environment, or incarnation.
>
> Stage 1 must not be split into separate sequential stages of harness, Cockpit, and reality model. Stage 1 is one minimum viable UMH organism: Reality Model + Cockpit + Memory + Governed Execution Loop.
>
> The harness cannot function as intended without the reality model and Cockpit. Cockpit without a reality model is only a dashboard. A reality model without Cockpit is inaccessible to the operator.
>
> Materialization Principle: If a human can imagine an outcome, UMH should attempt to simulate the path from imagination to materialization. Lack of current knowledge, resources, tools, capital, or information does not invalidate the intent; it creates acquisition loops, research loops, experiment loops, work packets, and time-bound execution paths.

**Classification:** OPERATOR CLARIFICATION -- not silently approved canon. Must be ratified as a design constraint before any implementation proceeds.

### 14.6C Reality Model Corrections (3 decisions)

#### DEC-146C-001: UMH Reality Model Identity

| Field | Value |
|-------|-------|
| Priority | P0 |
| Category | ARCHITECTURE / IDENTITY |
| Source | Operator clarification, 2026-06-04 |
| Affects | 17 UMH artifacts (listed above) |
| Blocks | All Cockpit implementation, all UMH reality-engine phases, Stage 1 build |

**Question:** Is UMH a reality-approximation engine that models 12 layers of reality isomorphically (physical, digital, cognitive, biological, social, economic, symbolic, operational, software, memory, source-truth, OS-level), or is it an operational orchestration kernel that manages execution and governance?

**Options:**
1. **Reality-approximation engine.** UMH's purpose is to approximate reality as closely and isomorphically as possible. The orchestration, governance, and execution capabilities are mechanisms that serve the reality model -- not the other way around. All 17 affected artifacts must be revised to reflect this framing.
2. **Operational orchestration kernel with reality-model aspirations.** UMH is primarily an orchestration system today, with a long-term vision to become a reality model. Current artifacts are accurate for current state; future phases add reality-model layers.
3. **Hybrid -- reality model IS the orchestration.** The reality model and the orchestration kernel are the same thing. Modeling reality accurately IS what enables governance, execution, and intelligence. No separate "reality engine" -- the substrate is the reality model.

**System recommendation:** Option 1. The operator clarification is unambiguous: "intended to approximate reality as closely and isomorphically as possible." This is the design intent, not a future aspiration.

| Source | Operator clarification, 2026-06-04 |

**System recommendation:** Option 1. The operator statement is unambiguous: "Stage 1 must not be split into separate sequential stages."
