#### DEC-146C-002: Materialization Principle as Core Design Constraint

| Field | Value |
|-------|-------|
| Priority | P0 |
| Category | DESIGN_PHILOSOPHY |
| Source | Operator clarification, 2026-06-04 |
| Affects | umh_execution_boundary_model.md, umh_governance_approval_lifecycle.md, all execution and planning systems |

| **Status** | **OPERATOR-APPROVED WITH MODIFICATION (2026-06-04)** |
| **Operator Selection** | **Option 1 modified** |

**Ratified Canon Statement:**

> If a human can imagine an outcome, UMH should attempt to simulate the path from imagination to materialization. Lack of current knowledge, resources, tools, capital, information, skill, access, or time does not invalidate the intent; it creates typed gaps and acquisition paths: research loops, resource acquisition loops, experiment loops, work packets, delegation paths, agent paths, financing paths, and time-bound execution paths. UMH should not treat current missing capability as terminal failure. It should classify the gap, identify what must be acquired or learned, generate the highest-leverage path, and govern execution. - This is a core design constraint, not aspirational.
- "Impossible" should not be used as lazy failure language.
- UMH must distinguish impossible, illegal, unsafe, unavailable, under-resourced, unproven, and not-yet-acquired.

**Original Options (for audit trail):**

2. Yes but bounded -- materialization within current capability.
3. Aspirational -- not a current design constraint.

**Resolution:** Approved with modification. Option 1 intent ratified. Operator expanded the gap taxonomy to include skill, access, and time. Added explicit safety/ethics boundary: outcomes violating physical reality, law, safety, ethics, or non-negotiable constraints are not materialized but are met with the nearest lawful/safe alternative.

#### DEC-146C-003: Indivisible Stage 1 -- Reality Model + Cockpit + Memory + Execution

| Field | Value |
|-------|-------|
| Priority | P0 |
| Category | ARCHITECTURE / STAGING |
| Source | Operator clarification, 2026-06-04 |
| Affects | All UMH Cockpit readiness artifacts, all Stage 1 planning, all MVP definitions |
| Blocks | Any phased/sequential Stage 1 build plan |
| **Status** | **OPERATOR-APPROVED (2026-06-04)** |
| **Operator Selection** | **Option B (Indivisible target, incremental build)** |

**Ratified Canon Statement:**

> Stage 1 is one minimum viable UMH organism: Reality Model + Cockpit + Memory + Governed Execution Loop. These components are not separate products or sequential phases. They must reach minimum viability as one integrated system. The harness cannot function as intended without the reality model. Cockpit without a reality model is only a dashboard. A reality model without Cockpit is inaccessible to the operator. Memory without execution is passive storage. Execution without memory, governance, and reality model state is unsafe and incoherent. Incremental builds are allowed only inside the indivisible Stage 1 target: each increment must advance the integrated organism across Reality Model, Cockpit, Memory, and Governed Execution rather than completing one component in isolation and deferring the others.

**Operator Constraints:**
- Reject sequential build framing.
- Accept incremental delivery only if increments advance the integrated organism.
- Stage 1 is not complete until all four components are minimally viable together.
- Do not define Stage 1 as a backend-only substrate.
- Do not define Cockpit as a passive dashboard.
- Do not defer reality model, memory, or governed execution to later phases.
- Do not require commercial-grade completeness before use.

**Operator Clarification — Stage 1 Minimum Viability (2026-06-04):**

The minimum version of UMH must provide a usable Jarvis-style operating experience. It does not need to be complete or final, but it must be functional enough for the operator to actually operate through it. "Indivisible Stage 1" does not mean all components are fully built before use. It means the minimum vertical slice must include partially functional Reality Model + Cockpit + Memory + Governed Execution together.

Stage 1 minimum viability acceptance criteria:

1. The operator can use Cockpit/Jarvis as the primary interface.
2. UMH can capture intent and preserve it in memory/source truth.
3. UMH can maintain a usable reality model of current work, products, companies, files, artifacts, agents, and blockers.
4. UMH can generate work packets from operator intent.
5. UMH can route work packets to agents/tools (Claude Code, shell, GitHub, docs, adapters).
6. UMH can govern risky actions through approval gates.
7. UMH can verify outputs through tests, audit reports, diffs, and review packets.
8. UMH can update memory/reality model after outcomes.
9. UMH can work on itself through governed self-improvement work packets.
10. UMH can build and improve projection apps from inside the UMH operating loop.

The minimum version must be usable enough for the operator to: get the Jarvis/workstation experience, run actual work through UMH, have UMH help build itself, have UMH help build EOS/CreatorOS/LyfeOS, then use those projection apps for their intended purposes, run real companies/life/content workflows through them, collect outcomes, and continue improving UMH and the projections from real usage.

Projection app minimum viability:
- EOS must be usable enough to run company operations.
- CreatorOS must be usable enough to run content/community/product workflows.
- LyfeOS must be usable enough to run personal execution/transformation workflows.

The correct target is an integrated, usable, self-improving UMH organism.

**Original Options (for audit trail):**
1. Indivisible Stage 1 (all four ship together or none ships).
2. Indivisible target, incremental build (each increment advances all four).
3. Sequential with parallel tracks.

**Resolution:** Approved Option B with Stage 1 minimum viability clarification. The operator selected the incremental-build variant and defined 10 concrete acceptance criteria for minimum viability. The target is a usable, self-improving organism — not a complete system or a backend-only substrate.
